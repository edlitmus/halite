# halite, for an agent picking it up

A reimplementation of Salt in Go: a hub, nodes, an API, a state engine, a
pillar compiler, and a module library. It manages a real fleet — this is
not a toy, and a bad change here reconfigures machines somebody depends
on.

This file is an orientation, not a manual. The authority is always
`SPEC.md`, and the fastest way to learn what this project believes is
`docs/DIVERGENCE.md`, which is a ledger of every place reality turned
out not to match what somebody assumed.

## The one rule everything else follows from

**A claim nobody demonstrated is a defect, whoever wrote it.**

That applies to code, to comments, to documentation and to your own
report at the end of a task. The project spends real effort making
undemonstrated claims *fail* rather than merely be wrong, so if you find
yourself about to write "this should work" — stop, and go and find out.
Several of the audits described below exist because somebody, including
previous agents on this codebase, did not.

Concretely, and these are not suggestions:

- **Do not raise an evidence level, close a ledger row, or mark
  something done because the code looks right.** Run it against the
  real tool. The release gate says so in its own failure text: *"Raising
  the level without doing the work is the one option that is worse than
  not having this gate, because it converts an unknown into a claim."*
- **Fixtures are captured, never written from documentation.** A test
  built from a man page tests the man page. This has cost real defects
  more than once; `getfacl -s`, `snap list` and `ps` are three of them.
- **When you fix something, break it again on purpose** and watch the
  test fail. A test that passes before and after your fix was not
  testing your fix.
- **Say what you did not verify.** In the commit, in the PR, and to the
  user. "Not yet run" is a perfectly good thing to write down, and it is
  much better than being wrong later.

## The shape of the commonest bug here

**Two paths that must agree.** Nearly every interesting defect in this
repository is a pair of things that are supposed to say the same thing
and do not: a parser and the tool it parses; a document and the code it
describes; a fixture and a real machine; a state's "is it converged?"
and its "make it converge". When you are hunting, look for the pair
rather than the symptom.

The second commonest is **an exculpatory conclusion**. A finding that
says "this is fine, because…" ends the investigation and then gets
written down, and the next reader finds a stated reason instead of an
open question. Those are worth more scrutiny than accusatory ones, not
less.

## Prose is a checked deliverable

`SPEC.md`, `plan.md`, `README.md`, `CHANGELOG.md` and everything in
`docs/` are held to the code **mechanically**, by tests that fail CI:

| Package | Holds |
|---|---|
| `internal/specaudit` | SPEC's module lists, totals and worked examples against the registry; the DIVERGENCE ledger's numbering, ordering and citations |
| `internal/docsaudit` | the generated docs against the code, and counts quoted in prose |
| `internal/buildpolicy` | the toolchain pin, the dependency allowlist, build flags, workflow/`go.mod` agreement |
| `internal/policy` | the lexicon, sandbox limits on shipped extensions |

So a change to a module is usually also a change to `docs/DIVERGENCE.md`,
sometimes to `SPEC.md`, and often to a count in three files you did not
expect. Run the audits; they will tell you exactly which. Do not edit
`docs/modules.md` or `docs/configuration.md` by hand — they are
generated by `go run ./tools/gendocs docs`.

### The ledger

`docs/DIVERGENCE.md` is numbered `N.M` inside chapters (`## 5.` …).
Entries are append-only in spirit: when something is fixed, add a
subsection under the existing number rather than rewriting history.
A section must sit inside the chapter its number names.

**Two branches in flight will both grab the next number**, and the audit
catches it on the second merge. Renumber yours, never main's — and do not
do it by hand:

```sh
go run ./tools/ledger next        # the next free number in each chapter
go run ./tools/ledger plan        # what renumbering would change
go run ./tools/ledger renumber    # do it
```

It works out which sections are yours by title, because the number is
what is in dispute; gives them the next free numbers; moves them to the
end of their chapter so the file still reads in order; and rewrites their
citations.

The last part is why the tool exists rather than a note saying "be
careful". Renumbering 5.149 to 5.151 means rewriting every citation of
5.149, and main may cite 5.149 meaning *its own* section — which must not
move. Nothing in the audits would catch that: they check a cited number
exists, not that it is the one meant. The tool rewrites a citation only
on a line your branch added, which `git diff` already knows, so the
distinction is made by construction rather than by judgement. Doing it by
hand meant a list of twenty-six file-and-line pairs, written out by
reading greps.

Run it **just before pushing for merge**, and again if `main` moves while
the PR waits: the number is only sound against the `main` you last saw.

One thing it cannot know: a number on a line you added that is an
*illustration* rather than a citation gets rewritten too. There is no way
to tell them apart from the text, so read `plan`'s list before running
`renumber` — it prints every line it would touch, and that is what the
list is for.

## Evidence, and the release gate

`internal/builtin/evidence.go` records, per module, how much anybody
actually knows:

- **`Assumed`** — tests written from documentation. The default, deliberately.
- **`Captured`** — tests hold output taken from the real tool, so parsing is checked; nothing has watched it *change* anything.
- **`Hardware`** — the mutating path has been run against the real tool on a real system, and the note says which and when.

`make release-gate` refuses a release while any root-mutating module is
`Assumed`. It currently passes. Keep it that way: a new module arrives
`Assumed`, which is correct, and closing it means finding a machine.

There are two honest ways past it — demonstrate the module, or take it
out of the build. Both have been used.

## The estate, and why FreeBSD comes first

Four FreeBSD hosts to one Ubuntu. FreeBSD is SPEC 27.1 **tier 1** and
carries about 80% of production. Ranking Linux work above FreeBSD work
is ranking one host above four.

**The development host, `beastie`, is FreeBSD — but an agent's shell
there is a Linux compatibility layer.** Never read the platform out of
your shell: `uname` lies to you specifically. Anything platform-sensitive
must be checked on a real machine of that platform.

And beware the reverse: because the dev host is FreeBSD, FreeBSD legs
*feel* covered when they are not. Two separate defects shipped because
the machine in front of somebody had a flag that the platform in general
does not (`shutdown -c`, `getfacl -s`).

## Where things run

- **`make check`** is the local gate: `fmt-check vet build-all test race policy fips-test`.
- **`.github/workflows/ci.yml`** — unit, race, fmt/vet/policy, build-all, reproducible build, the Salt differential, FIPS, on Linux/macOS/Windows/FreeBSD.
- **`.github/workflows/fleet.yml`** — the *live* legs, which drive real tools as root: `debian`, `linux`, `freebsd` (an emulated VM) and `macos`. Triggered by a schedule, a dispatch, and changes to the modules they cover. If you add a live test, add it to the right leg's `-run` filter and to the trigger paths, or it will never run again.
- **`.github/workflows/release.yml`** — two builders, all artifacts compared byte-for-byte, then keyless SLSA provenance for the digests they agreed on (only after the release gate passes). The binaries are kept for three days as a workflow artifact; nothing is published as a release yet. Runnable by `workflow_dispatch` without minting a tag, which writes a real, permanent Sigstore log entry for that commit.

### Live tests

Named `TestLive*`, gated on `HALITE_SYSTEM_LIVE=1` and usually root.
They skip with a message saying *why* on a machine that cannot run them,
and that message is part of the output people read. A test that skips is
not a test that ran — if you are relying on one, prove it executed.

### The lab

`contrib/tofu` raises throwaway cloud instances: seven Linux
distributions and FreeBSD 14 and 15. `make lab-up`, `lab-wait`,
`lab-facts`, `lab-test`, `lab-down`.

**They bill until `make lab-down`.** Tear them down in the same session
you raised them, and check `lab-hosts` if you are unsure.

Two traps recorded there: a long run's output must survive it (do not
pipe a sweep through `tail`; do not edit the driver while it is
running), and Vultr's BSD images do not run cloud-init — they boot from
a base64 startup script instead.

## Build and tooling notes

- **The `Makefile` is BSD make.** There is no `$(shell …)`; use `!=`. A
  GNU-ism fails quietly, not loudly. Recipe lines are separate shells.
  The reverse trap is on a Mac: `/usr/bin/make` is GNU make 3.81, which
  ignores `!=` silently, so build and install targets refuse to run under
  it (`make-supports-bang`). Use `bmake` or `gmake` there; `make check`
  still works with the stock one.
- **One vendored dependency**, `golang.org/x/sys`, under a closed
  allowlist that `internal/buildpolicy` enforces. Adding one is a SPEC
  change and almost certainly the wrong answer — the project's own rule
  is to drop scope before breaking that constraint.
- **Vendored builds**: `GOFLAGS=-mod=vendor GOPROXY=off`. The release
  path also pins `-trimpath`, `CGO_ENABLED=0` and `SOURCE_DATE_EPOCH`.
- `go test` caches results and several audits read the whole repo, so
  pass `-count=1`.
- Under `go test` a binary carries no commit stamp, so version tests can
  pass on a broken build.

## Working conventions

- **Branch, PR, CI green, merge.** Do not commit to `main`. Pull before
  pushing — other sessions land work on `main` mid-task.
- **One commit per logical change.** If you find a second defect while
  fixing the first, it gets its own commit, usually its own PR.
- Commit subjects are imperative and under 72 characters, prefixed
  `feat:`/`fix:`/`docs:`/`test:`/`ci:`/`chore:`. The body explains *why*,
  and names what was measured rather than what was intended.
- The comments in this codebase are unusually long and explain
  reasoning, especially why an obvious alternative is wrong. Match that.
  Do not add comments that restate the code.
- If a defect is worth fixing it is worth a ledger entry; if it changes
  what an operator sees, it is worth a `CHANGELOG.md` entry.

## Finding your feet

1. `docs/DIVERGENCE.md` — read a dozen recent sections. They are the
   project's accumulated experience, and they are written to be read.
2. `plan.md` §7 — the ranked order of what is worth doing next, with the
   reasoning for the ranking.
3. `make release-gate` — what the project will not ship on today.
4. `internal/builtin/evidence.go` — how much is actually known about
   each module, in its own words.
